## Confirmed findings to fix before new features

### 1. High priority: backdated entries can replace the apparent current regimen

**Synthetic reproduction:** save and approve an INR dated 12 November, 35 mg/week, next INR 19 November. Then enter and approve an older result dated 29 October, 21 mg/week, next INR 5 November.

**Observed:** the latest measured result remains 12 November and backend `approvedPlan_()` selects 35 mg/week. The frontend's **Current clinician-approved care plan** instead shows 21 mg/week, its recorded dose selects 21 mg/week, and the page's next INR becomes 5 November. Care-plan draft preparation fails with “The latest result still needs clinician approval before messaging,” even though both encounters are approved.

**Cause:** frontend encounter/dose/follow-up selection uses append order (`.at(-1)`); backend approved-plan selection sorts by effective date. Message guards again use append order. The historical encounter's previous-dose baseline also comes from the last appended plan, which can be later in clinical time.

**Locations:** [care status](../app/js/care-ui.mjs#L11), [approved-plan display](../app/js/care-ui.mjs#L68), [passport/current dose](../app/js/app.js#L280), [passport dates](../app/js/app.js#L619), [previous-dose selection](../backend/API.gs#L290), [server approved plan](../backend/API.gs#L1172), [message guard](../backend/API.gs#L1280).

**Next task:** establish and test one consistent chronology for current clinical decisions, historical entry and monitoring dates across frontend/backend. Entering historical information must not silently replace the active plan or fabricate its previous-dose comparison. Define historical-entry handling with the owner; ask before any schema or clinical authorization change. Preserve all existing records. Test older entries, same-day results, drafts and approvals separately.

### 2. Medium priority: a successful telephone call never clears the “inform patient” task

**Synthetic reproduction:** approve a plan, record a `Contacted` follow-up documenting that the plan was explained by phone, and explicitly complete that encounter's follow-up. Do not create a WhatsApp/manual-message record.

**Observed:** the backend follow-up is `Completed`, but `careStatus().informed` stays false and the dashboard still lists one patient awaiting a care plan. This happens because successful contact is gated on a separate `Sent manually` care-plan communication.

**Location:** [careStatus](../app/js/care-ui.mjs#L15).

**Next task:** let a deliberately documented, successful contact about the relevant approved plan count regardless of communication channel. Keep a message opening, sending alone, failed contact, or completion of an unrelated encounter insufficient. Review whether the current UI distinguishes “made contact” from “explained this plan” clearly enough before changing completion rules.

### 3. Medium priority: encounter notes are displayed twice; amendments lack visible relationships

**Synthetic reproduction:** create one encounter containing a clinical note. Saving creates both `Encounters.note` and a linked `Clinical_Notes` record. The patient page merges both and displays that note twice. Two such encounters produced four displayed entries for two source notes.

**Locations:** [save](../backend/API.gs#L370), [merged notes](../app/js/app.js#L628).

**Next task:** render each linked note once, retain legacy encounter-only notes, and show amendments as amendments with the original retained and clearly marked. Deduplicate by record/encounter linkage, not by matching text across unrelated entries. No deletion of records is needed.

### 4. High priority: an open INR form can save to a different patient after keyboard navigation

**Browser reproduction (isolated synthetic demo):** open `DEMO-001`, select **Enter a new INR**, enter INR 2.4, then use Shift+Tab to reach the background **Patients** navigation. Press Enter, Tab to `DEMO-002`, and press Enter. The original INR form remains open. Complete and save it.

**Observed:** `DEMO-001` stays at six results; `DEMO-002` gets a seventh result and the reason entered in the first patient's form. The form has no patient name/MRN inside it. Focus remains outside the dialog when it opens, and Tab can activate background navigation despite `aria-modal=true`. The connected save path also resolves `getPatient()` at submission rather than binding the form to its original patient; that part was inspected in code, not exercised against live records.

**Additional usability observation:** cancelling an edited form discards it without confirmation. Care-message dialogs already include an identity strip, so protection is inconsistent.

**Locations:** [generic modal](../app/js/app.js#L842), [background navigation/dismiss](../app/js/app.js#L1240), [connected submission lookup](../app/js/app.js#L1419), [message identity strip](../app/js/care-ui.mjs#L95).

**Next task:** bind every clinical form to its original patient ID/version and reject a changed context at submission; put patient name/MRN in the dialog; make background controls inert, focus and contain navigation, and restore focus on close. Verify with a regression test that the keyboard sequence cannot save to another patient. Add **Keep editing / Discard** only for dirty forms. Preserve in-memory drafts during ordinary tab changes; do not introduce clinical local-storage caching. No live patient was accessed in this reproduction.

## Engineering and operational follow-up

- **One Pages publisher:** GitHub's Pages API currently reports `build_type: legacy` on main `/`, while the Actions workflow also publishes `app/`. The live site currently has the correct stamped assets; there is no observed outage. Choose GitHub Actions as the single publisher to remove a deployment race and simplify cache diagnosis.
- **Cloudflare PR previews:** the prior preview check still fails immediately; production main builds have worked. The previous handoff gives the dashboard setting: root `gateway`, non-production command `npx wrangler versions upload`, or an explicit decision to disable non-production builds. Do not change Worker/build configuration without owner approval. This review did not access Cloudflare account settings or logs.
- **Scalability:** the API still reads the full tab history and returns up to 200 active patient bundles. Per-request caching is useful, but it does not remove growth in historical reads or patient/day limits. Measure real request times before choosing pagination/indexing. The current UI does warn when the loaded cohort reaches 200.
- **Maintainability:** `app/js/app.js` is 1,704 lines and `backend/API.gs` 1,641. Split by view/domain in separate refactor PRs after fixing behavior; keep existing tests. Three layered stylesheets and DOM-driven translation need gradual consolidation rather than another full redesign.
- **Midnight:** the browser's `TODAY` is initialized once. A long-lived session can keep yesterday's due/stale calculations after Riyadh midnight. Recompute the clinic day on visibility/refresh without dropping forms; add a clock-controlled test.
- **Guides:** `USER_GUIDE.md` and `CLINICAL_METHODS.md` still contain patient-request/portal wording and an obsolete patient-access-security reference despite removal. Update documentation to the staff-only workflow, current button labels and session-restore behavior.
- **Clinical source review:** the requested AC Forum PDF remains unverified in the documented implementation. Verify the document/version before adding its rules. UW percentage/monitoring rules, emergency thresholds, TTR exclusions and historical-target handling still need clinical-owner validation; code tests alone do not validate treatment policy.
- **Shared iPad privacy:** an optional clinic-agreed idle lock is worth discussing. It changes sign-in/session behavior and requires owner approval. Do not add it during a visual cleanup.
